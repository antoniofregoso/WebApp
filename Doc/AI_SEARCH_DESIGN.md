## Problem

WebApp is a template for generating applications whose models and views are defined
through schemas. Search must work automatically with any model that declares
`search: true`, without adding application-specific logic.

Users can write questions such as:

> Show me Antonio's urgent tasks that are due this week.

The AI does not answer from invented knowledge and does not generate SQL. Its only
job is to convert the question into a structured `SearchPlan`. The backend validates
the plan against the schemas, applies permissions, and queries PostgreSQL.

## Goals

- Automatically discover every model with `search: true`.
- Support traditional search and natural-language questions.
- Apply the same permissions used by regular views.
- Return real, identifiable, linkable records.
- Keep the AI provider optional and interchangeable.
- Allow a webapp to disable AI functionality completely.

## Initially out of scope

- Embeddings and vector storage.
- Searching the binary content of attachments.
- Generating answers without record references.
- Performing updates or deletions from search.
- SQL generated by the AI model.

## Approved assumptions

1. Only models with `search: true` participate.
2. Only fields explicitly allowed for search are exposed.
3. The AI produces JSON that conforms to a strict contract.
4. The backend validates models, fields, operators, relations, and permissions.
5. Results include links to real records.
6. Ambiguous queries request clarification before execution.
7. Traditional search remains available when AI is disabled.

## Declarative configuration

### Canonical source

The canonical search source is `system_models.json`, not the view schema.
`system_model_schemas.json` continues to control presentation only. The seed process
persists this configuration in PostgreSQL:

- `SystemModel.search`: boolean, `false` by default.
- `SystemModelField.search_config`: JSONB, `{}` by default.

Every change requires an Alembic migration, a seed update, and a synchronization
test. The persisted database is the execution source; JSON is the versioned source
for new installations. `search` is not duplicated in view schemas.

### Enabled model

`search` is added to the `system.model` definition and defaults to `false`.

```json
{
    "name": "system.task",
    "label": {
        "es_MX": "Tareas",
        "en_US": "Tasks"
    },
    "search": true
}
```

### Searchable fields

Each field's `search` property controls what search may interpret, filter, and
display. If it is omitted or `false`, the field never leaves the backend for the AI
provider.

```json
{
    "name": "title",
    "type": "string",
    "search": {
        "enabled": true,
        "text": true,
        "result": "title",
        "weight": "A"
    }
}
```

```json
{
    "name": "date_due",
    "type": "datetime",
    "search": {
        "enabled": true,
        "filter": true,
        "operators": ["eq", "before", "after", "between", "this_week"]
    }
}
```

```json
{
    "name": "user_id",
    "type": "many2one_avatar",
    "model": "user.user",
    "search": {
        "enabled": true,
        "filter": true,
        "relation_fields": ["name", "email"]
    }
}
```

### Recommended minimum configuration

- `enabled`: allows the field to be used.
- `text`: includes the field in text search.
- `filter`: allows structured filters.
- `result`: defines whether it is the result title, subtitle, or snippet.
- `weight`: `A`, `B`, `C`, or `D` priority for text relevance.
- `operators`: explicitly narrows the allowed operators.
- `relation_fields`: limits navigable fields on a relation.

## SearchPlan v1

The AI provider must produce only this contract. The backend never accepts a SQL
expression inside the plan.

```json
{
    "version": 1,
    "intent": "search_records",
    "queries": [
        {
            "model": "system.task",
            "text": null,
            "filters": {
                "and": [
                    { "field": "priority", "operator": "eq", "value": "Urgent" },
                    { "field": "user_id.name", "operator": "contains", "value": "Antonio" },
                    { "field": "date_due", "operator": "this_week", "value": null }
                ]
            },
            "order": [
                { "field": "date_due", "direction": "asc" }
            ],
            "limit": 20
        }
    ],
    "needs_clarification": false,
    "clarification_question": null
}
```

### Contract limits

- `version` allows the contract to evolve without breaking existing applications.
- `queries` contains 1 to 5 subplans; each subplan belongs to one model.
- Only one logical level is allowed: `{ "and": [...] }` or `{ "or": [...] }`, never
  arbitrarily nested trees. The default is `and`.
- Each subplan allows up to 10 filters, 3 order clauses, and 20 results. The server
  enforces a global maximum of 50 results.
- An order field must declare `search.filter: true` and use a sortable type.
- Results are grouped by model. Scores are not compared across models.
- Properties for tables, physical columns, or executable SQL are forbidden. User
  values may contain words such as `SELECT` or `DROP`; they are always treated as
  parameterized data.
- Relative dates are resolved with the user's timezone and language.
- An invalid plan is rejected, not silently repaired.

### Normative contract

`SearchPlanV1`, `ModelSearchQuery`, `FilterGroup`, `SearchFilter`, and `SearchOrder`
are Pydantic models with `extra="forbid"`. Their enums contain only the operators in
this specification. JSON Schema is generated from Pydantic and is the same schema
received by the AI adapter. `version`, `intent`, `queries`, `needs_clarification`,
and `clarification_question` are required; the backend assigns the remaining
defaults. No output is executed before passing both Pydantic validation and
validation against persisted metadata.

When `needs_clarification` is `true`, `queries` must be `[]` and
`clarification_question` is required. When it is `false`, `queries` contains 1 to 5
items and `clarification_question` must be `null`.

Rejected examples include a model without `search`, a nonexistent field, an
operator outside the enum, more than 5 subplans, unknown properties, and an
unauthorized relation.

### Value shapes

| Operator | `value` shape |
|---|---|
| `eq`, `gt`, `gte`, `lt`, `lte`, `before`, `after`, `contains`, `starts_with` | A scalar compatible with the terminal type |
| `in`, `not_in`, `contains_any`, `contains_all` | Array of 1 to 20 unique scalars |
| `between` | Exact `[start, end]` array where start does not exceed end |
| `today`, `this_week`, `this_month` | `null` |

Dates use ISO 8601; datetimes must include an offset. Decimals travel as decimal
strings to avoid precision loss. `eq: null` is not allowed: null filters may be
added in a later version with explicit operators. Strings have a maximum length of
500 characters.

## Operators by type

| Type | Initial operators |
|---|---|
| `string`, `text`, `html` | `eq`, `contains`, `starts_with` |
| `selection`, `status_badge`, `color` | `eq`, `in`, `not_in` |
| `integer`, `decimal`, `monetary`, `percentage` | `eq`, `gt`, `gte`, `lt`, `lte`, `between` |
| `boolean` | `eq` |
| `date`, `datetime` | `eq`, `before`, `after`, `between`, `today`, `this_week`, `this_month` |
| `many2one`, `many2one_avatar` | `eq`, `in`, and permitted related fields |
| `many2many`, `many2many_pills` | `contains_any`, `contains_all` |

The validator derives this list from the field type and then restricts it with
`search.operators` when declared by the schema.

For `user_id.name`, operators come from the terminal `name` type, but the path is
valid only when `user_id.search.relation_fields` contains `name` and
`user.user.name` is also enabled. `relation_fields` never expands permissions. The
compiler also applies the related model's authorization policy inside the `EXISTS`.
A sensitive field cannot be enabled even when it belongs to an authorized relation.
If the related model has no registered policy, the full path is rejected.

## Time resolution and localization

- `today`, `this_week`, and `this_month` are calculated in the user's timezone and
  then converted to UTC boundaries for PostgreSQL.
- `this_week` uses an ISO week, from Monday 00:00 inclusive to the following Monday
  exclusive.
- Localized selection labels are resolved to their technical values before
  compilation. "Urgente" becomes `Urgent`.
- Exact technical-value matching is attempted first, followed by a localized-label
  match in the user's language.
- If two localized values match, the plan requires clarification.
- The timezone must be a valid IANA identifier. If it is missing, the application's
  configured timezone is used; if that is also missing, `UTC` is used, never the
  server timezone.

## Interpreter catalog

`SearchableSchemaV1` contains a version, language, timezone, and up to 20 models.
Each model includes its technical name, localized label, and up to 50 fields with a
name, type, label, summarized help, operators, selection values, and permitted
relations. It contains no records or real values. If an installation exceeds 20
models, the backend first looks for a normalized exact match between query words and
declared technical names, labels, or aliases. It narrows the catalog only when there
is exactly one match. If there is no match, or several matches, it returns
`NEEDS_CLARIFICATION` with up to 10 model options; it never silently excludes models
using fuzzy similarity. The complete catalog is also validated with Pydantic before
being sent.

## Recommended architecture

```text
TopbarSearch
    │
    ├── traditional search ────────────────┐
    │                                      │
    └── natural-language question          │
            │                              │
            ▼                              │
      SearchInterpreter                   │
      (AI adapter)                         │
            │ SearchPlan                   │
            ▼                              │
      SearchPlanValidator ◄── schemas + permissions
            │ validated plan               │
            ▼                              │
      SearchQueryCompiler ◄────────────────┘
            │ parameterized query
            ▼
        PostgreSQL
            │
            ▼
      SearchResult[] + links
```

### Backend

- `SearchSchemaService`: discovers enabled models and fields.
- `SearchInterpreter`: provider-independent AI interface.
- `SearchPlanValidator`: validates the plan and returns typed errors.
- `SearchQueryCompiler`: transforms only validated plans into parameterized
  SQLAlchemy queries.
- `SearchService`: orchestrates interpretation, validation, execution, and auditing.
- `SearchRepository`: executes queries without knowing about prompts or providers.

Only models present in `MODEL_CLASS_BY_NAME` participate. A parallel
`SEARCH_MODEL_REGISTRY` declares the ORM class, authorization function, and URL
builder without changing existing `MODEL_CLASS_BY_NAME` consumers. A model with
`search: true` but without all three capabilities fails during startup, not during a
user query.

Many-to-many relations compile to `EXISTS`, not joins that multiply rows.
Pagination uses a stable order with `uuid` as its final criterion.

### Proposed GraphQL API

```graphql
query Search($input: SearchInput!) {
  search(input: $input) {
    requestId
    status
    interpretedQuery
    needsClarification
    clarificationQuestion
    results {
      model
      modelLabel
      uuid
      title
      subtitle
      snippet
      url
      score
    }
    errors {
      code
      message
      model
      field
    }
  }
}
```

```graphql
input SearchInput {
  query: String!
  mode: SearchMode! = AUTO
  model: String
  limit: Int = 20
  originalQuery: String
  clarificationAnswer: String
}

enum SearchMode {
  AUTO
  TEXT
  AI
}
```

`status` accepts `OK`, `PARTIAL`, `NEEDS_CLARIFICATION`, and `FAILED`. Initial typed
errors are `INVALID_PLAN`, `MODEL_NOT_ALLOWED`, `FIELD_NOT_ALLOWED`,
`OPERATOR_NOT_ALLOWED`, `AI_UNAVAILABLE`, `TIMEOUT`, and `INTERNAL_ERROR`. A failure
in one model produces `PARTIAL` without hiding valid results from other models.

The first version does not paginate within a group; it applies the limit per
subplan. A later version may add per-model cursors without changing `SearchResult`.

In a normal request, `query` is required and clarification fields are `null`. For a
clarification, `query` retains the complete new input, `originalQuery` and
`clarificationAnswer` are required, and the server limits each one to 2,000
characters. The client never sends a previous plan.

`interpretedQuery` is a localized summary generated deterministically from the
validated plan, for example, "Tasks with Urgent priority assigned to Antonio." It is
neither provider free text nor a serialized plan.

### Provider adapter

```python
class SearchInterpreter(Protocol):
    async def interpret(
        self,
        query: str,
        searchable_schema: dict,
        context: SearchContext,
    ) -> SearchPlan: ...
```

Configuration selects the adapter. No domain directly imports an AI SDK.

Every adapter must support JSON Schema or return text that passes the same local
validator. If it cannot produce a valid `SearchPlanV1` in one attempt,
`INVALID_PLAN` is returned; there is no autonomous retry loop. Timeout: 10 seconds.
In `AUTO`, `AI_UNAVAILABLE`, `TIMEOUT`, or `INVALID_PLAN` runs TEXT with the original
query and returns `PARTIAL` with a warning. Explicit `AI` mode returns `FAILED` with
no silent fallback.

## Traditional search

Search without AI uses the same field catalog and returns the same result type. The
first phase may use parameterized matching. When volume justifies it, PostgreSQL
Full Text Search can be added with `tsvector`, `tsquery`, ranking, and GIN indexes.

This keeps one contract for the frontend, permissions, and navigation.

### Phase 1 TEXT algorithm

1. Normalize whitespace and limit the query to 500 characters.
2. Split into terms and escape `ILIKE` wildcards.
3. For each enabled model, apply every term with `AND`; within each term, search with
   `OR` across every `search.text: true` field.
4. In Phase 1, `html` fields cannot declare `search.text: true`. They may contribute
   snippets after another field finds the record. Searching their content requires
   a normalized column that is updated on write and indexed; HTML is never cleaned
   during every query.
5. Score within each model: exact title match `100`, title prefix `70`, title
   contains `50`, other-field contains by A/B/C/D weight `40/30/20/10`. Sum and sort
   by descending score, then title and UUID.
6. Group results by model. Scores are never compared across models.

For multiple models, the effective limit is
`min(SearchInput.limit, ModelSearchQuery.limit, 20)`. The global maximum of 50 is
allocated in `queries` order; each subplan consumes up to its limit and the final one
is truncated when the budget is exhausted. Subplan order is part of the plan.

The initial implementation uses parameterized expressions. The benchmark records
PostgreSQL, CPU, RAM, concurrency, and field count and size. If it misses the SLO,
Phase 1 may use `pg_trgm` indexes; FTS remains the path for linguistic ranking.

## Security

- Authentication is required for every query.
- The catalog sent to AI contains only permitted schemas.
- Values from `password` fields, tokens, secrets, or fields with `search: false` are
  never sent.
- Users may query only records they could open in a normal view.
- `SearchAuthorizationPolicy` is created before search is enabled. It may initially
  adapt existing per-model policies; equivalence tests guarantee that search and
  views authorize the same record set. Incremental internal migration of views to a
  shared policy follows later. The policy receives the user, company, and ORM class
  and returns SQLAlchemy conditions. This is Phase 0 and blocks later phases.
- Every condition is built with SQLAlchemy and bound parameters.
- Model, filter, relation, depth, and result counts are limited.
- Auditing records `request_id`, user, models, duration, status, result count, and an
  HMAC-SHA256 of the query. Query text and plan values are not stored by default.
  Initial configurable retention is 30 days and cleanup runs when a new entry is
  written.
- The response distinguishes zero results, invalid queries, ambiguity, and provider
  errors.
- Search is initially read-only.

## User experience

1. The user opens search from the topbar.
2. They enter keywords or a complete question.
3. In `AUTO`, a configured provider enables AI interpretation; otherwise `TEXT` is
   used. Users may explicitly select `TEXT` to avoid sending a query to a provider.
4. An explicit loading state is shown while processing.
5. Results are grouped by model and display a title, context, and link.
6. Missing information produces a clarification question in the same panel.
7. The user opens a record without losing the previous query.

Clarification is stateless: the client resends `originalQuery` and
`clarificationAnswer` in a new request. The server combines them into interpreter
input. No conversation is stored, and a client-provided plan is never trusted.

`title`, `subtitle`, and `snippet` are built on the server from declared fields.
Only one `result: "title"` may exist; the first configured subtitle is the fallback.
HTML is converted to text, escaped, and truncated to 240 characters. The URL is
built from the secure model registry as `/dashboard/user/{model}/{uuid}`.

### Required states

- Initial state with example questions.
- Loading.
- Results.
- No results.
- Clarification required.
- AI disabled or not configured.
- Provider temporarily unavailable.
- Query not permitted.

## Rejected approaches

### Direct AI-to-filter translator

It is fast, but combines interpretation, validation, and execution. That makes
testing, security, and provider changes harder.

### Vector-based hybrid search from the start

It adds indexing, synchronization, cost, and permission rules before proving that
structured search is insufficient. It remains a possible future evolution.

## Implementation phases

### Phase 0: authorization and secure registry

1. Create a shared per-record and per-company authorization policy.
2. Extend the model registry with ORM class, policy, and URL builder.
3. Verify that views and search produce the same authorized set.

### Phase 1: contract and text search

1. Add `search` and `search_config` to the model, migration, seed, and documentation.
2. Define `SearchPlan`, `SearchResult`, and error types.
3. Implement discovery, validation, and permissions.
4. Implement text search and the GraphQL API.
5. Connect the topbar panel.

### Phase 2: AI interpretation

1. Create `SearchInterpreter` and a configurable adapter.
2. Generate the plan's JSON Schema from enabled models.
3. Implement clarification queries.
4. Add limits, auditing, timeouts, and failure handling.
5. Create a set of evaluations in Spanish and English.

### Phase 3: relevance and scale

1. Measure latency, zero-result queries, and user corrections.
2. Add PostgreSQL Full Text Search when basic text search is insufficient.
3. Consider embeddings only when metrics reveal conceptual queries that fields,
   filters, or full-text search cannot solve.

## Required tests

- A model without `search: true` never appears and cannot be queried.
- A field that is not enabled never appears in the catalog and cannot be filtered.
- Fields, operators, relations, and models invented by AI are rejected.
- Per-user and per-company record restrictions are respected.
- Dates such as "this week" respect the timezone.
- Localized selections are converted to technical values.
- HTML is converted to safe snippet text.
- Zero results are not presented as an error.
- A provider outage preserves traditional search.
- Links open the correct model and UUID.
- The maximum limit applies even when the plan requests more.
- Malicious queries do not alter generated SQL.
- `AUTO` uses AI when configured and falls back to `TEXT` when it is not.
- Canceling a search causes the frontend to ignore late responses.
- Results always have stable ordering and are not duplicated by relations.
- A failure in one model returns `PARTIAL` with typed errors.
- A clarification resends the original question without executing client plans.
- Any invalid subplan atomically fails the whole plan before querying. `PARTIAL` is
  reserved for execution failures after the complete plan has been validated.

## Success criteria

- 100% of results belong to enabled models and fields.
- No test can bypass user or company permissions.
- An application enables a registered model by modifying its canonical definition;
  a new ORM model must also register authorization and a URL.
- The first ten reference queries produce valid plans and correct results in Spanish
  and English.
- Traditional search works without an AI provider key.
- The 95th percentile for text search remains below 300 ms in a reproducible
  benchmark with 100,000 records per model, 5 searchable fields, 10 concurrent
  clients, and documented hardware, excluding AI time.
- The 95th percentile for AI interpretation is measured separately and has a
  timeout.

## Observations

- The phrase "this is a template for generating webapps" correctly changed the
  decision: search must be declarative and optional, not a task-specific feature.
- You chose "every model with `search: true`," a simple rule that lets each
  application control its scope without changing search code.
- You asked for documentation before implementation. In a template, the contract is
  more important than choosing an AI provider early.
